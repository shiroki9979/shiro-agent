# 採用 coding agent 時代的註解策略

> 建立日期：2026-11-21
> 最後更新：2026-11-21
> 依據：[Coding agent 時代的程式碼註解策略調查](code-comments-for-coding-agents-research.md)

這份指南給想替自己的專案訂註解規則的團隊，目標是讓人和 coding agent 都能安全地修改程式碼。它只講原則和判斷準則，不規定標籤語法、檢查實作或工具設定；這些請依專案的語言與工具自行決定。

核心想法只有一句：**agent 讓「讀程式碼」變便宜，但沒有讓「推錯」變少，而且留下的註解會被它當成指令執行。** 所以重點不是註解寫多寫少，而是每一條留下來的註解都說了程式碼說不出來的事，而且它一旦過時，會有人或工具發現。

## 名詞

- **重述型註解**：只把名稱、型別、簽章或下一行程式碼換句話說的註解。
- **why-not 註解**：放在看起來不合理、多餘或任意，其實是刻意如此的程式碼旁邊，說明背後的限制、實際觀察到的失敗，或當時的決策依據。
- **天條**：模組或類別標頭中，任何修改都必須維持的不變條件，也就是新呼叫端或新增函式最可能破壞的規則。
- **錨點**：註解明確指名它保護的程式碼，或它指向的另一份來源，讓工具能判斷這條註解是否已經失去對象。
- **介面文字**：會被工具讀取並成為對外輸出的文字，例如變成 API 文件或命令列說明的 docstring。

## 七條原則

### 1. what 交給名稱、型別與程式碼

**為什麼**：研究顯示，拿掉註解對 LLM 理解程式碼「做什麼」幾乎沒有影響，但前提是名稱保留；名稱被混淆後，理解就大幅下滑。實驗中全刪註解的版本仍理解 97% 的 what。扛起 what 的是名稱，不是註解。

**怎麼判斷**：刪掉這條註解後，讀者只看名稱和型別會不會誤會？不會就刪。會的話，先試著改名稱或拆函式，而不是補註解。

但要分清楚：名稱和型別表達不了的**介面語意**不是重述，例如前置條件、副作用、會丟出的例外、執行緒安全性等假設。這類內容 Ousterhout 和主流 style guide 都要求保留，因為 agent 沒有跨工作階段的記憶，每次都得重新推導介面，而推導就可能出錯。

### 2. why 寫在改動現場，並指名它保護的程式碼

**為什麼**：why 幾乎無法從程式碼還原。實驗中全刪註解後，理解「為什麼這樣寫」從 94% 掉到 60%。ADR 和 commit 訊息雖然記錄了 why，但站在程式碼前動手修改的人或 agent 看不到它們。

**怎麼判斷**：問自己：「下一個人或 agent 會不會想把這段『修正』掉？」會，就需要 why-not 註解。換一種說法：下次 code review 時需要口頭解釋的，現在就寫下來。架構層級的 why 放在 ADR，現場只要留一句指向它。

why-not 註解要指名它保護的是哪段程式碼。這樣程式碼被移除時，註解失去對象，就能被發現並一起刪掉。Rust 的 `// SAFETY:` 慣例是現成的先例：搭配 clippy 的兩個選用 lint，可以要求每個 `unsafe` 區塊旁都說明為何安全，並禁止這種註解出現在沒有 `unsafe` 的地方。

### 3. 天條要能失敗

**為什麼**：把一條散文寫成「天條」，提高了它的權威，卻沒有讓它變得可驗證。模型會照單全收它讀到的規則，所以一條寫錯或過時的天條，會被 agent 拿來對抗正確的程式碼。

**怎麼判斷**：能寫成型別、驗證器、斷言或測試的不變條件，就寫成可執行的形式，標頭只要陳述它並指向那個檢查。違反時會失敗的天條，才是真正的天條。真的無法執行化的，至少要寫明由哪份文件或哪個審查環節負責把關。

### 4. 過時的註解比沒有註解更危險

**為什麼**：在已發表的研究中，這是最一致的發現。錯誤或過時的註解造成的傷害，遠大於沒有註解；而且明確叫模型「忽略註解」並沒有用。註解越少、份量越重，這個風險就越集中。

**怎麼判斷**：每條留下的註解，都要能回答「它過時了，誰會發現？」答不出來的，就是應該刪除或改成可執行檢查的候選。修改程式碼時，相關的註解要在同一次變更裡一起更新或刪除。

### 5. 約束註解的形狀與錨點，不約束數量

**為什麼**：字數或行數上限會引發 Goodhart 效應，資訊會被擠進超長的名稱、移到別處，或直接消失。實驗中刪掉 64% 字元的版本，漏掉了現狀版抓到的 10 個陷阱 bug 中的 4 個。另一方面，規則越明確，不同人執行的結果越一致；模糊的規則連兩次改寫都對不齊。

**怎麼判斷**：不要設數量上限。規則要規定的是「註解可以是哪幾種」以及「每一種必須指向什麼」，讓不符合形狀的註解進不來，而不是讓有價值的註解被配額擠掉。

### 6. 工具會讀的 docstring 是介面文字，不能當註解刪

**為什麼**：很多框架會讀 docstring，把它變成 API 文件、schema 說明或命令列說明。直接刪除會改變對外輸出，甚至讓程式啟動就崩潰；而且通常沒有任何測試會發現。例如 FastAPI 會把路由的 docstring 變成 OpenAPI 說明；用 `__doc__` 組出命令列說明的程式，在 docstring 被刪掉後可能一啟動就出錯。

**怎麼判斷**：動手清理前，先盤點哪些 docstring 會被工具讀取。比較好的做法是把這些文字搬到框架提供的明示參數，讓契約顯性化，也能用測試鎖住。

### 7. 跨模組的契約用連結取代重述

**為什麼**：同一條契約若同時寫在規格文件和程式碼標頭，兩份副本中通常只有一份有「同步更新」的守門，另一份遲早會過時，變成原則 4 警告的那種註解。

**怎麼判斷**：契約已經有單一來源（規格文件、ADR）時，標頭只放連結；只在本模組內成立的不變條件，才寫在本模組的標頭。

## 機械檢查與人工審查的分工

機械檢查負責形狀與錨點，人工審查負責內容與必要性。機械檢查只能保證註解「長得對、指得到」，不能保證它說的是真的。

| 適合機械檢查 | 留給人工審查 |
| :--- | :--- |
| 註解是否屬於規則允許的種類 | 這條註解是不是只在重述 |
| 錨點是否仍指向存在的程式碼或檔案 | why 的內容是否正確、是否必要 |
| 是否有被註解掉的程式碼 | 天條是否仍然成立 |
| 天條指向的檢查是否存在 | 函式的介面語意是否交代清楚 |
| 介面文字是否還在（例如對 API 文件做快照測試） | 新規則是否逼出了樣板式註解 |

要提防一種失敗模式：為了通過檢查，agent 在每一行都貼上形式正確、內容空洞的註解。錨點要求可以擋掉一部分，剩下的要靠審查。

## 導入步驟

1. **盤點現況**：分別量出行內註解和 docstring 的數量，找出哪些 docstring 是介面文字，哪些註解在扮演天條。冗餘不一定在直覺以為的地方：行內註解可能早已精簡，冗餘反而集中在 docstring。
2. **先清冗餘**：只刪重述型註解，逐條審查，不要批次刪除。這一步本身就有證據支持：實驗中刪掉約三分之一註解的版本，各項指標都看不出損失。
3. **再加約束**：把規則寫進人和 agent 都會讀的團隊規範。檢查只針對新增或修改的部分，舊程式碼改到哪裡、清到哪裡，不要一次產生巨大的 diff。如果用 coding agent，讓檢查在 agent 寫入當下就回饋，不要等到 CI 才失敗。
4. **把天條轉成檢查**：逐條把散文不變條件改寫成型別、驗證器或測試，並讓標頭指向它。
5. **每一步分開進行**：每個階段都是獨立、可以單獨回退的變更。

## 怎麼知道有效

可以持續追蹤這些訊號：

- 沒有錨點或不屬於允許種類的註解，數量是否持續下降。
- 檢查抓到多少失去對象的註解或過時的天條。
- 審查中，因為缺少 why 而被「修正」掉的刻意設計是否減少。
- agent 的修改被退回時，原因是否和註解有關。

如果想用實驗證明某條規則比較好，請參考研究報告中較嚴謹的設計：配對設計、足夠多的陷阱（約 50 個以上才有足夠的檢定力）、加入「註解已過時」的組別、加入「應該直接執行」的對照任務、使用不同家族的讀者模型，並且盲評。

## 這份指南的限制

- 支撐這些原則的研究大多是 2025–2026 年的預印本，也還沒有直接比較不同註解策略對 agent 影響的對照研究；原則是從間接證據推導出來的。
- 「錨點」和「天條要能失敗」是推論出來的設計，還沒有在任何專案中經過實作驗證。第一個實際導入的專案應記錄結果，並回饋到這份指南。
