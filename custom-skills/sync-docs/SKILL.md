# 文件同步檢查規範（Sync Docs）

本技能用於指導專案程式碼實際狀態與既有技術文件之間的交叉比對、過時/缺漏診斷與安全自動同步。以程式碼為單一真實來源（Single Source of Truth），精準校正過時描述，並與既有文件規範協同運作。

---

## 1. 核心原則與安全邊界

1. **程式碼為單一真實來源（Code as Source of Truth）**：
   - 當文件記載與目前程式碼實作不一致時，原則上以程式碼為準修復文件。
   - 若程式碼近期變更與既有架構設計有明顯邏輯矛盾或疑似引入 Regression，標記為「需確認」，不強行修改文件。
2. **兩階段安全修正（Two-Phase Safe Modification）**：
   - 第一階段：掃描專案並產出全域診斷表格，標記狀態（`最新`、`需更新`、`需確認`、`缺漏`）。
   - 第二階段：針對確定性過時項目（API 簽名、CLI 指令、相對路徑、設定欄位）就地修正；歧義與架構變更列出選項由使用者決策。
3. **保持既有格式與語氣（Style Preservation）**：
   - 僅修正過時事實與技術細節，保留原文件的語氣、章節結構、標題層級與排版風格。
4. **規範協同防護（Standard-Compliant Guardrails）**：
   - 嚴格遵守各類型特定文件的固有規範（如 ADR 歷史不改寫、CHANGELOG 格式、Diátaxis 象限純度）。

---

## 2. 智慧檔案探索與排除範圍

### 自動探測範圍

掃描時優先自動探測以下路徑下的所有 Markdown（`.md`、`.mdx`、`.mdc`）文件：

- **根目錄標準文件**：`README.md`、`AGENTS.md`、`CONTRIBUTING.md`、`DEVELOPMENT.md`、`SECURITY.md`。
- **文件專用目錄**：`docs/`、`doc/`、`documentation/`、`guides/`。
- **模組/子套件說明**：各子套件目錄下的 `README.md`（例如 `src/*/README.md`、`packages/*/README.md`、`tests/README.md`）。

### 自動排除清單（Exclusions）

以下目錄一律略過，不列入一般比對與修改範圍：

- 版本控制與快取：`.git/`、`.svn/`、`__pycache__/`、`.pytest_cache/`、`.mypy_cache/`。
- 相依套件與虛擬環境：`node_modules/`、`.venv/`、`venv/`、`env/`、`site-packages/`。
- 建置產出與編譯目錄：`dist/`、`build/`、`out/`、`target/`、`.next/`。
- 歷史封存與過渡目錄：`docs/archive/`、`labs/archive/`、`history/`、`tmp/`、`temp/`。

## 3. 比對維度與稽核矩陣（Verification Matrix）

執行交叉比對時，依循以下六大面向進行逐項查核：

| 面向 | 比對焦點 | 程式碼來源依據 | 常見過時徵兆 |
| :--- | :--- | :--- | :--- |
| **模組與 API 簽名** | 類別/函式名稱、參數名稱、型別標註、預設值、回傳格式 | `src/`、模組原始碼、型別定義檔（`.py`、`.ts`、`.go` 等） | 函式已增減參數或重新命名，但文件仍記載舊簽名 |
| **CLI 指令與腳本** | 建置、測試、部署、啟動指令與參數 | `Makefile`、`package.json` scripts、`pyproject.toml`、CLI entry points | 指令名稱變更、參數選項廢棄或新增必要 flag |
| **設定檔與環境變數** | 設定檔欄位、環境變數名稱、預設值、服務拓撲 | `.env.example`、`compose.yml`、`Dockerfile`、設定檔 schema | 配置項已更名、預設 port 變更、依賴服務增減 |
| **導覽與相對路徑** | 文件內部連結、程式碼參照路徑、圖片參照 | 專案目錄結構與實際檔案位置 | 檔案已搬移/改名/刪除，文件連結失效產生 404 死連結 |
| **架構與流程描述** | 核心資料流、依賴分層、管線階段、模組職責 | 系統入口點、資料管線邏輯、核心介面實作 | 架構已重構拆分，但文件仍描述舊有單體或淘汰流程 |
| **Metadata 時間戳** | `Last Updated: YYYY-MM-DD` 或 `最後更新` | 當前日期與檔案實質修改紀錄 | 文件內容已修正但時間戳未刷新 |

## 4. 執行流程步驟（Step-by-step Protocol）

### 步驟 1：收集程式碼現狀

執行唯讀指令與程式碼檢索，掌握專案實作現況：

```bash
# 掌握近期變更脈絡
git log --oneline -20
git diff --stat HEAD~10 HEAD 2>/dev/null
```

同時針對專案關鍵程式碼進行盤點：

- **進入點與介面**：掃描核心模組之公開 class、function 簽名與資料結構。
- **任務與自動化**：檢查 `Makefile`、`package.json` 或建置設定中定義的任務。
- **測試範疇**：檢查 `tests/` 結構，確認實際支援的功能與驗證範圍。
- **配置與容器**：檢查 Dockerfile、Compose 服務或部署組態。

---

### 步驟 2：逐一交叉比對文件

依據探索到的文件清單，對照「比對維度表」逐份驗證：

1. **文字描述核實**：比對文件中的 API 範例程式碼、CLI 執行指令是否可真實重現。
2. **連結有效性檢核**：驗證文件中所有相對路徑（`[text](../path/file.md)`）目標是否存在。
   - 若目標檔案僅是搬移或重新命名，自動校正相對路徑。
   - 若目標檔案已徹底刪除且無替代品，標記為「需確認」。
3. **架構語意一致性**：比對架構圖、流程說明與現行模組互動關係。
4. **缺漏功能辨識**：若掃描到新加入之核心模組、重要 CLI 指令完全未在任何文件中提及，標記為「缺漏」。

---

### 步驟 3：產出標準化診斷報告

在進行任何寫入前，先整理出全域診斷表格，狀態分為四類：

- **最新（Up-to-date）**：文件內容與程式碼完全相符，無須更動。
- **需更新（Needs Update）**：存在確定性之過時事實（API、指令、路徑），可直接安全修正。
- **需確認（Needs Confirmation）**：存在架構矛盾、疑似 Bug 或涉及多個候選設計方向。
- **缺漏（Missing）**：程式碼具備重要功能但完全無對應文件記載。

---

### 步驟 4：安全修正與骨架建議

1. **直接修正「需更新」項目**：
   - 精確修正過時之函式名稱、參數、型別、指令與失效連結。
   - 若文件有實質變更，且頂部包含 `Last Updated` 或 `最後更新`，刷新為當前日期（`YYYY-MM-DD`）。
   - 若文件為「最新」無實質變更，保持原時間戳不變動。
2. **處理「需確認」項目**：
   - 不自行猜測修改，於報告中列出具體衝突點與建議方案，等待使用者指示。
3. **處理「缺漏」項目**：
   - 於報告中提供建議建立之文件路徑、Diátaxis 象限分類與最簡骨架結構，待確認後再行建立。

---

## 5. 既有文件規範協同防護

當同步涉及專案中受特定規範管轄的文件時，必須遵循該規範的邊界限制：

### A. 架構決策紀錄（ADR）

- 依循 `adr-writing` 規範。
- **歷史不回頭改寫原則**：嚴禁直接修改已核准（Accepted）ADR 的決策語意與歷史推論。
- **允許修正範圍**：僅限於補充 `Notes` 中的取代關係連結、修復失效之外部檔案相對路徑，或追蹤狀態流轉。

### B. 變更日誌（CHANGELOG）

- 依循 `changelog` 與 Keep a Changelog 規範。
- 僅在 `## [Unreleased]` 區塊進行條目增修，不任意篡改已發布（Released）歷史版本的內容。

### C. Diátaxis 結構化文件

- 依循 Diátaxis 結構化框架規範。
- 修復或補充內容時，嚴格維護該文件所屬象限之純度（Tutorial 禁止塞入 API 字典、Reference 禁止寫入入門教學），避免象限污染。

## 6. 輸出結構與格式模板

輸出結果時，統一採用以下結構呈現：

### 區塊一：文件診斷報告（Diagnostic Table）

```markdown
### 文件同步診斷報告

| 文件路徑 | 比對面向 | 狀態 | 診斷說明 | 處理動作 |
| :--- | :--- | :--- | :--- | :--- |
| `docs/pipeline/overview.md` | 架構/CLI | 需更新 | Pipeline 階段參數與現行 CLI `run-pipeline` 不一致 | 修正指令參數與資料流說明 |
| `README.md` | API 簽名 | 需更新 | 範例程式碼引用已廢棄之舊 class 名稱 | 更新為新 class 名稱 |
| `docs/adr/0002-auth.md` | 相對路徑 | 需更新 | 參照之舊模組路徑已搬移 | 校正為現有相對路徑 |
| `docs/architecture/flow.md` | 架構描述 | 需確認 | 記載同步處理，但程式碼已改為非同步佇列 | 列出選項待確認 |
| `docs/guides/new-engine.md` | 新功能 | 缺漏 | 核心模組 `EngineV2` 缺乏操作手冊 | 建議建立 How-to 骨架 |
| `CONTRIBUTING.md` | 指令正確性 | 最新 | 建置與測試指令與現行 Makefile 完全相符 | 無需更動 |
```

### 區塊二：修改摘要（Modification Summary）

針對已修正的檔案，每份提供 3~5 行重點摘要（標註檔案路徑、修改重點與時間戳刷新狀態）：

```markdown
### 修正摘要

- **[docs/pipeline/overview.md](file:///path/to/docs/pipeline/overview.md)**：
  - 更新 CLI 範例指令為現行 `run-pipeline --batch`。
  - 同步資料流程圖中新增的驗證步驟。
  - 刷新 `Last Updated` 為 2026-08-24。

- **[README.md](file:///path/to/README.md)**：
  - 校正快速入門範例中的模組引入路徑。
```

> 若全數文件皆與程式碼一致，無任何需更新或需確認項目，僅輸出一句確認：「經比對，專案現有文件與程式碼狀態完全一致，無須更新。」

## 7. 品質驗收檢核表（Quality Checklist）

在完成文件同步作業後，執行以下檢核以確保品質：

| 檢核項目 | 合格標準 |
| :--- | :--- |
| **真實來源** | 所有修正皆以現有程式碼或近期 Git 提交紀錄為依據，無隨意臆造 |
| **無破壞性修改** | 保持原文件語氣、排版與結構，僅替換過時之事實內容 |
| **時間戳精準** | 僅實質修改之檔案刷新 `Last Updated`，未更動之檔案保持原樣 |
| **無懸空死連結** | 修正後的文件相對路徑經核實皆指向有效目標 |
| **規範無衝突** | ADR 未篡改歷史決策、CHANGELOG 遵循 Keep a Changelog、Diátaxis 象限無污染 |
| **需確認項目明確** | 所有具爭議或架構矛盾項目皆清晰標記並提供決策選項，未擅自定奪 |
